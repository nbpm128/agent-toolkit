# Artifact templates

> How every planning-dev artifact is created and what shape it takes; the template files themselves are in `assets/`.

## Copy, then fill

Never transcribe a template from memory: copy the file, then replace all three placeholder kinds:

| In the template | What to do with it |
|---|---|
| `{{something}}` | substitute the value |
| `[a sentence of guidance]` | replace the whole block with the real content |
| `<!-- a comment saying what goes here -->` | write what it describes, and delete the comment |

Braces are used rather than `<Title>` because a renderer swallows an angle placeholder as an unknown tag, so an unfilled one would show up as nothing, while braces render literally and stay greppable. That is a rule about the templates, not about chat: the message skeletons use `<...>` on purpose, since they are read inside fenced blocks where nothing is rendered.

| Phase | Copy | To |
|---|---|---|
| research | `assets/research.template.md` | `plans/plan-<name>/research.md` |
| planning | `assets/plan.template.md` | `plans/plan-<name>/plan.md` |
| planning | `assets/task.template.md` | `plans/plan-<name>/tasks/task_NNN_<slug>.md`, once per task |
| acceptance | `assets/acceptance.template.md` | `plans/plan-<name>/acceptance.md` |

`tasks/_index.md` has no template; the script creates it. A leftover placeholder is a plan failure, and a reviewer catches it.

## What each file holds

The tree is in `SKILL.md`, section "Artifacts"; a sub-plan folder repeats it one level down.

| File | Holds |
|---|---|
| `research.md` | what was found and decided, with the assumption registry |
| `plan.md` | the roadmap: goal, architecture, constraints, milestones, shared context, traceability |
| `acceptance.md` | an append-only dated log of acceptance runs |
| `tasks/task_NNN_<slug>.md` | one task, written for an executor who sees only it and `plan.md` |
| `tasks/_index.md` | generated by the script, never edited |

## The shape every document takes

```
---
{{machine fields}}
---

# {{Type}}: {{Title}}

> {{one line: what this document is and what happens next}}

N. {{Section}}
```

The block shows the outline only; real documents write each section as a heading `## N. Section`.

| Part | Rule |
|---|---|
| Frontmatter | machine fields only |
| Title | `<Type>: <Title>`, so the type shows in a file listing |
| Purpose line | one line saying what the document is and what happens next |
| Section numbers | stable, because other documents cite them; task files use fixed unnumbered headings instead |

The exception is `acceptance.md`, which is an append-only dated log.

The text inside every artifact follows the rules for every text in `references/presentation.md`, section 2: enumerations of three or more items as lists or tables, one kind of information per section, a fact stated once and referred to by its id elsewhere, an open question written with what it blocks.

## Generated blocks

`tasks/_index.md` in full and the counts block in `plan.md` §7 are written by `--sync` between a start marker and `<!-- END GENERATED -->`, and are never edited by hand. The start marker is `<!-- BEGIN GENERATED -->` in `tasks/_index.md` and `<!-- BEGIN GENERATED: counts -->` in `plan.md` §7. To set a status, edit the task's frontmatter and run `--sync`; nothing else needs keeping in step.

## Field rules

**Research**

- `updated` is the day the document last changed, the same field and meaning as in a task file; `plan.md` uses `created` instead, because its own history is the Revision Log.
- `status` is `draft` until the user accepts.
- `confidence` holds a number from 0 to 100 (High above 85, Medium 66-85, Low below 66); planning reads the class, where Medium means a proof-of-concept slice first.
- The Decision & Requirements section gives each requirement a stable `REQ-NNN`.
- The Assumption registry has the columns `ID`, `Assumption`, `Status` (`verified`, `user-decided`, `unverified`), `Evidence`, `Relates to`. Evidence is a `file:line` quote, command output, or `unchecked user statement: "<short quote>", <date>`.
- The Revision Log records every amendment.

**Plan**

- `status` is `draft` until the user accepts at Gate 2b, then `approved`.
- `elaboration` is `up-front` or `just-in-time`, chosen at Gate 2a; it says whether every task file exists when the plan is accepted or each one is written at its own entry in Phase 3.
- The `Tasks` cell in §4 reads `task_NNN — <title>`.
- "Accepted" in §6 flips to `yes` only with acceptance evidence.
- The §7 counts are generated.
- Append a row to §9 on every revision.

**Task**

- `NNN` is a zero-padded three-digit number, and a written file's number never changes.
- `depends_on` may use the short form (`task_003`) or the full stem.
- `assumptions` lists `ASM` ids.
- The `>` line under the title is what the index shows, so it must read on its own.
- A task file never names this skill, its path or its scripts.
- Files has the columns `Action`, `Path`, `What changes`.
- The Decision log may be `None.`
- A test scenario written in the Acceptance section opens with one line saying it is fictitious and what it is for, so its invented names are not read as part of the project.
- A `delegated` task replaces its Instructions with a pointer to the sub-plan and keeps its Acceptance unchanged.

**Acceptance**

- Append a dated section per run, never overwrite an earlier one.
